Critical theater in the only UI test, and a confirmed sanitizer bypass with no test to catch it.
The Swift suite is substantial and mostly real: 443 tests exercise real Git repositories, real file descriptors, real SSH sessions, and real WKWebView instances. The green build is still not a strong signal, because the two paths that most need a test either assert nothing or are not reached at all.
Plain-language summary

The test suite is largely genuine. Most Swift tests drive real dependencies rather than stand-ins, and the remote transport harness runs the production connection code over a pipe instead of faking it. That is the right shape, and it means most of the 443 Swift tests would notice if the code beneath them broke.

Two things undercut it. The HTML sanitizer, which is the only barrier between untrusted Markdown and script execution inside the embedded browser, has a bypass that its 49 tests do not cover: a link scheme padded with two or more tab or newline characters passes the sanitizer untouched, and the browser then strips that padding and runs the script. This was confirmed by execution, not inferred. Separately, the sole user-interface test performs a PDF export and asserts nothing, deferring verification to a script that also asserts nothing and reports that manual checking is recommended.

Beyond those, the command the project designates for local verification builds the app without running any test at all, so the routine developers are told to follow never executes the suite. The remote helper's main file-read entry point lacks the safety checks its sibling asset-read path received, and has no test. Two renderer modules, one of which decides which line of the user's document a checkbox click rewrites, have no test coverage of any kind. Three tests skip themselves silently when the environment does not cooperate, and the test log records a claim that no such skips exist.
